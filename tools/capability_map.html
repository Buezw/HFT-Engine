01

一笔挂单的一生

这是最容易读代码也读不出来的部分——一笔挂单从"挂上"到"消失"之间，到底能被谁、怎么改。

02

撮合核心

市价单怎么吃掉盘口——从最优价位开始，一档一档往后吃，直到吃满或者没货了。

ob_market_buy_baseline / ob_market_sell_baseline
main.c 原始逻辑：逐档吃单，自成交（is_mine）在玩家自己下单时会被跳过
ob_market_buy_opt / ob_market_sell_opt
同样的外部行为，内部把 total_qty 顺手维护好，不用每 tick 重新扫一遍
03

价格漂移

最早这几个价位是死的，挂了就再也不动——库存倾斜策略在这种市场里根本没有"行情跟你作对"这种风险可以防。这个函数是补上"市场自己会动"这件事之后加的。

ob_drift_price_*
把买卖两边所有价位一起挪 delta，价差和档位间距不变——只是整个梯形挪了位置。它自己不决定"什么时候挪、挪多少"，跟市价单一样，由外面的场景/测试来喂
诚实的简化：这本书永远只有固定的 MAX_PRICE_LEVELS 档，不像真实盘口那样价位是随订单动态出现/消失的。所以"漂移"本质是把这几个固定档位的价格标签整体重贴，而不是真的生成新档位——挂在某一档里的单子，成交价会跟着这一档"现在"的价格走，不是挂单那一刻的价格。这是现有数据结构带来的真实限制，不是这个功能引入的新 bug。
04

挂单生命周期

main.c 从来没写过"自己挂一个限价单"的功能——虽然到处都在检查 is_mine，就是没有地方把它设成 1。这一整块是补全的，不是移植的。

ob_place_limit_buy_* / ob_place_limit_sell_*
挂一笔限价单，买单立刻冻结现金、卖单立刻冻结库存——跟真实限价单一样，挂上就占用资金
ob_cancel_order_*
按 id 撤单，退还冻结的资金/库存；重复撤同一个单会被拒绝，不会退两次钱
ob_modify_qty_*
原地改数量：id、队列位置都不变，加量要有钱/有货，不够就拒绝，什么都不改
ob_modify_price_*
挪价位：本质是撤旧单+挂新单，拿新 id；新单挂失败的话旧单原样保留，不会两头落空
05

风控

main.c 的市价单完全没有仓位上限——随机压测直接把库存打到 -168,805，暴露出这个洞之后才补上的。

ob_market_buy_risk_checked_* / ob_market_sell_risk_checked_*
套在市价单外面的一层，把请求数量削减到 MAX_POSITION（500）以内——削减、不是直接拒绝，0 笔成交也是合法结果
只管玩家自己的仓位——模拟盘口那边的市场噪音单不归这个风控管，因为那不是"自己的仓位"。
06

O(1) 索引

书浅的时候（板子上实际只有 60 笔单子）挨个扫一遍完全不是问题；书一旦变深，"挨个扫"就扫不动了。

ob_place_limit_*_opt_indexed / ob_cancel_order_opt_indexed
挂单/撤单的同时维护一张 order_id → 位置 的哈希表
ob_modify_qty_opt_indexed / ob_modify_price_opt_indexed
改单也走同一张哈希表，不用重新扫全书
07

并发基础设施

撮合本身永远单线程（一本账必须按顺序处理）。能并行的是"收单子"和"真正撮合"这两件事。

spsc_push / spsc_pop
无锁的单生产者/单消费者队列，两个线程之间传消息不用加锁
意外发现：把两个线程强行绑定到指定 CPU 核心上，反而制造出一个稳定复现的 ~12.5ms 超长卡顿——这是台大家共用的机器，绑核心相当于关掉了操作系统"帮你避开拥堵"的能力。
