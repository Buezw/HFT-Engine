这个引擎到底能干什么

不用看代码的功能清单——每个能力配一句大白话说明，加上对应的函数名（方便回代码里查），蓝色是 baseline，琥珀色是 opt。两者用的是同一本盘口、同一套撮合，唯一的区别是按 order_id 找单子的方式。

01

一笔挂单的一生

这是最容易读代码也读不出来的部分——一笔挂单从"挂上"到"消失"之间，到底能被谁、怎么改。

02

撮合核心

市价单怎么吃掉盘口——从最优价位开始，一档一档往后吃，直到吃满或者没货了。

ob_market_buy_* / ob_market_sell_*
从最优价位开始逐档吃单；玩家自己下单时会跳过自己的挂单（不自成交）。baseline 和 opt 这里是同一套代码，opt 只是顺手更新一下索引
现在还缺的一块：只有市价单会撮合。限价单挂到对手价里面也不会成交，就那么挂着——盘口会交叉。
03

动态盘口

最早这本书是定长数组，每边固定 MAX_PRICE_LEVELS 档——板子上没有 malloc，只能这么写。真实数据把这个设计打穿了：跑一整天 GOOG，最优买价卡在开盘的 $579.40，而真实市场已经跌到 $565.12。原因不是算错了，是窗口外的价格从来就没被记录过，顶档抽干之后引擎根本不知道下一档在哪。

现在每边是一个 std::map<价格, 档位>，每档一个 std::deque 按时间排队。有单子才有这一档，最后一笔走了这一档就没了，深度不设上限——跟真实交易所一样。同一天 GOOG 重跑，最优买价跟到了 $565.10，差两分。
ob_num_levels / ob_level_price / ob_level_qty / ob_level_order_at
盘口结构体是不透明的，外面只能通过这些函数读；level_index 从最优价位数起，0 就是最优
ob_qty_at_price
直接查某个价格上挂了多少——跟 LOBSTER 那种"只列有单子的价位"的表示法对账时，这就是一次查表，不用再还原成密集的逐 tick 视图
ob_books_equal
baseline/opt 的深度比较：档位、数量、每档的排队顺序全对上才算相等
顺带删掉的东西：价格漂移（ob_drift_price_*）、ghost 订单和 clean_ghosts 压缩、update_total_qty 重扫。这些都是定长数组才需要的补丁，动态结构里没有对应的问题。
04

挂单生命周期

main.c 从来没写过"自己挂一个限价单"的功能——虽然到处都在检查 is_mine，就是没有地方把它设成 1。这一整块是补全的，不是移植的。

ob_place_limit_buy_* / ob_place_limit_sell_*
挂一笔限价单，买单立刻冻结现金、卖单立刻冻结库存——跟真实限价单一样，挂上就占用资金
ob_cancel_order_*
按 id 撤单，退还冻结的资金/库存；重复撤同一个单会被拒绝，不会退两次钱
ob_modify_qty_*
原地改数量：id、队列位置都不变，加量要有钱/有货，不够就拒绝，什么都不改
ob_modify_price_*
挪价位：本质是撤旧单+挂新单，拿新 id；新单挂失败的话旧单原样保留，不会两头落空
ob_cancel_order_any_* / ob_reduce_order_qty_any_*
同样的撤单/减量，但针对别人的单子：不看 is_mine，也没有退款（人家本来就没冻结）。跑真实行情数据靠的就是这两个
还没补上的：挂买单时不检查现金够不够（改数量的时候检查），所以现金能被挂成负的。
05

风控

main.c 的市价单完全没有仓位上限——随机压测把库存打得远远超出合理范围，暴露出这个洞之后才补上的（当时报出来的具体数字后来发现一部分是另一个记账方向 bug 造成的，见下方"O(1) 索引"之后那一节，但"没有仓位上限"这个结论本身没变）。

ob_market_buy_risk_checked_* / ob_market_sell_risk_checked_*
套在市价单外面的一层，把请求数量削减到 MAX_POSITION（500）以内——削减、不是直接拒绝，0 笔成交也是合法结果
只管玩家自己的仓位——模拟盘口那边的市场噪音单不归这个风控管，因为那不是"自己的仓位"。
06

O(1) 索引

书浅的时候（板子上实际只有 60 笔单子）挨个扫一遍完全不是问题；书一旦变深，"挨个扫"就扫不动了。这就是 baseline 和 opt 现在唯一的区别。

baseline 的 cancel / modify / *_any
从最优档开始，一档一档、一笔一笔扫，直到找到这个 order_id
opt 的同名函数
内部带一张 order_id → (方向, 价格) 哈希表，挂单/成交/撤单时顺手维护。查的时候直接定位到那一档，只扫这一档
07

一个记账方向的 bug

ob_market_buy_opt/sell_opt（还有 baseline）把两种不同的成交，当成同一种方向来记账：玩家自己主动下单成交（方向对）和别人的单子吃掉了我挂在盘口的单子（方向应该相反，之前写反了）。这两个引擎自己的测试从来没抓到过——因为 baseline 和 opt 犯的是一模一样的错，"两边对得上"这件事本身骗过了所有测试。真正抓到它的，是 Market-Maker-Strategy 那边一个全新的库存风控测试。

"测试全绿" ≠ "代码是对的"——这是这个项目讲得最透的一课，比之前那个数组越界的 bug 更彻底：那个后来被 ASan 自己抓到了；这个只能靠"检查经济逻辑对不对"的外部测试才能发现，光靠内部一致性永远抓不到。
修复方式：两个方向共用同一套公式，加一个 sign = is_player ? 1 : -1——玩家自己下单那条路径（sign=1）完全不变，被噪音单吃掉自己挂单那条路径（sign=-1）方向翻正。baseline/opt 同步改，改完重新跑一遍全部测试，两边依然完全一致——只是现在算出来的具体数字是对的。
08

并发基础设施

撮合本身永远单线程（一本账必须按顺序处理）。能并行的是"收单子"和"真正撮合"这两件事。

SpscRing::push / SpscRing::pop
无锁的单生产者/单消费者队列，两个线程之间传消息不用加锁
意外发现：把两个线程强行绑定到指定 CPU 核心上，反而制造出一个稳定复现的 ~12.5ms 超长卡顿——这是台大家共用的机器，绑核心相当于关掉了操作系统"帮你避开拥堵"的能力。
09

验证与工具

这个项目的核心纪律：先证明"一样"，才谈"更快"。

tests/test_correctness.cpp
20 万 tick 回放 + 几组随机压测（10 万/5 万/2 万次），每一步都比对 baseline/opt 状态
tools/lobster_replay.cpp
拿真实 NASDAQ 数据跟交易所自己重建的盘口对账：AAPL/GOOG/AMZN 三个完整交易日、51 万行，0 条不一致
tests/test_spsc_ring.cpp
200 万条消息的真·双线程压测，专门跑在 ThreadSanitizer 下（ASan 抓不到数据竞争）
bench/*.cpp + make visualize
延迟分布（p50/p99）、深度扫描、可拖动的网页版盘口回放
这两件事证明的不是一回事：baseline/opt 对账只能说明两个实现一致，说明不了它们是对的——上面那个记账方向的 bug 就是两边一致地错。LOBSTER 对账是外部真值，但它只走到"挂单/按 id 减量/按 id 撤单"，撮合、账户、风控它一条都没碰。
